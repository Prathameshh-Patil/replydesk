# Deploying ReplyDesk

Three pieces need hosting, each on a free tier:

| Piece | Host | Why this one |
|---|---|---|
| PostgreSQL | **Neon** (Free plan) | Managed Postgres that doesn't expire. Render's free Postgres is deleted 30 days after creation. |
| API (FastAPI, Docker) | **Render** (free web service) | Runs our existing `backend/Dockerfile` unchanged, deploys from GitHub. |
| Front end (Next.js) | **Vercel** (Hobby plan) | Built by the makers of Next.js; zero configuration. |

## Free-tier limits (checked 2026-10-12; they change, so re-check)

- **Neon Free**: 1 GB storage per project, 100 compute-hours per project per month, the database suspends after 5 idle minutes and wakes in about a second. Our data is a few MB.
- **Render free web service**: 512 MB RAM, 0.1 CPU, 750 instance-hours per month per workspace. **It sleeps after 15 minutes without traffic, and the first request after that takes about a minute.** The login page says so while it waits.
- **Vercel Hobby**: free for personal, non-commercial projects; 100 GB transfer and 1M function calls per month.
- **Groq free tier** (the model): about 1,000 requests and 200K tokens per day for `openai/gpt-oss-120b`. One ticket is 4 calls and about 4,500 tokens, so roughly **40 tickets a day**. The demo caps new tickets at 25 a day (`DAILY_TICKET_LIMIT`) to leave room for reruns.

## Step by step

### 1. Database (Neon)

1. Sign in at https://neon.com, **New project**, name `replydesk`, Postgres 17, region **AWS Asia Pacific (Singapore)**.
2. **Connect** → turn **Connection pooling off** (migrations want a direct connection) → copy the connection string. It looks like `postgresql://user:password@ep-xxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`. It is a secret: don't paste it anywhere but Render and your own terminal.
3. Nothing else to do here: when the API starts it runs the migrations (`alembic upgrade head`) and creates the demo staff account named in `DEMO_EMAIL` with a random password nobody knows (`app/demo.py`). The only way into that account is the "Try the demo" button.

### 2. API (Render)

1. Sign in at https://render.com with GitHub. **New → Blueprint**, pick the `replydesk` repo. Render reads `render.yaml`.
2. It asks for the three secret values:
   - `DATABASE_URL`: the Neon string from step 1.
   - `LLM_API_KEY`: your Groq key (https://console.groq.com/keys).
   - `CORS_ORIGINS`: leave as `https://example.com` for now; you'll set it after step 3.
3. **Apply**. The first build takes a few minutes. When it's live, open `https://<your-service>.onrender.com/health`: it should say `{"status":"ok","environment":"production"}`.

`JWT_SECRET` is generated by Render. `ENVIRONMENT=production` makes the API refuse to start with a weak secret.

### 3. Front end (Vercel)

1. Sign in at https://vercel.com with GitHub. **Add New → Project**, import `replydesk`.
2. **Root Directory**: `frontend`. Framework: Next.js (detected).
3. **Environment Variables**: `NEXT_PUBLIC_API_URL` = `https://<your-service>.onrender.com` (no trailing slash).
4. **Deploy**. Note the address, e.g. `https://replydesk.vercel.app`.

### 4. Connect them (CORS)

In Render → the service → **Environment**, set `CORS_ORIGINS` to the exact Vercel address (for example `https://replydesk-kappa.vercel.app`, no trailing slash) and save; Render redeploys. Without this the browser blocks every call from the front end to the API.

### 5. Demo tickets

So the inbox isn't empty for the first visitor, import the 8 messages in `demo/tickets.csv` (written for the demo, not taken from the eval set). They go through the real agents (8 × 4 calls).

```sh
API=https://<your-service>.onrender.com
TOKEN=$(curl -s -X POST $API/auth/demo | python3 -c "import sys, json; print(json.load(sys.stdin)['access_token'])")
curl -s -H "Authorization: Bearer $TOKEN" -F file=@demo/tickets.csv "$API/tickets/import"
```

Expected: `{"created":8,"errors":[]}`. They count towards today's limit of 25.

### 6. Auto-deploy from `main`

Already on: Vercel deploys every push to `main` (and makes a preview for every pull request), and Render deploys `main` once GitHub Actions CI has passed (`autoDeployTrigger: checksPass` in `render.yaml`).

### 7. Checks after deploying (on your phone)

1. Open the Vercel address on your phone (mobile data, not your Wi-Fi, to be sure it's really public).
2. **New message**: write in as a customer.
3. **Log in → Try the demo**; open your ticket and watch the four steps finish.
4. Edit the draft, **Approve with edits**; check it shows as approved and edited.
5. **Stats**: the counts and chart include your ticket.
6. Optional: set `DAILY_TICKET_LIMIT` to the number of tickets created today, send one more message, and check you get the "try again tomorrow" message; then set it back to 25.

## What the live demo deliberately allows

Anyone can log in as the demo staff account and approve, reject or rerun any ticket, and read every message visitors wrote. That's the point of a demo, so the form warns visitors to use made-up details. A real deployment would leave `DEMO_EMAIL` empty, which switches the one-click login off.
